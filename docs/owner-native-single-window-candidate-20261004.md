# One captured M1 LAN native-event window candidate

The default-OFF helper/driver adapter now supports an explicit trusted local
M1 LAN diagnostic selection. There is no CLI, environment or HTTP opt-in. The
ordinary saved-UI CLI still accepts only its existing public owner scope. A
future independent coordinator passes a validated `owner_native_window.Window`
to the driver; that object contains expected metadata, not operator permission,
server guest ownership or live admission. The finite gateway/coordinator is not
implemented or run by this change.

The new helper mode requires LAN45560/45963, media-only, the actual V50 button
profile30FPS/540P/4M VBR/80ms, AAC, lead0 and stage/startup/PCM queue OFF. It uses
only the normal App scope callback and existing encrypted credential restore.
The actual destination, existing huoguo/wyw account and nonempty editable must
match. The helper never converts the password to a String, reads the store or a
private input, copies a public secret to LAN, or saves a replacement credential.
If the one stored destination is public and no LAN entry restores, it declines
before starting an owned Attempt. Account eligibility is not operator identity.
Two actual-method JVM fixtures exercise a LAN-specific normal restore and refusal
of a public-only stored entry; neither is a real Keystore/phone acceptance.

The descriptor must actually report30seconds and enabled native diagnostics.
The helper waits at most8seconds for initial worker/callback progress, then
observes one1–10second window, default5seconds. It checks the same captured
Attempt, UI and activity generations, receiver and valid Surface at each bounded
sample. Up to44 rows use the phone's System.nanoTime; worker and callback reads
are not atomic with that timestamp. A stalled counter is retained as evidence,
not renamed no packet loss. These counts are not presented or unique-content
FPS. No source input, UiAutomation, SF sampler, marker barrier, microbenchmark
or reconnect is performed by the selected mode.

The phone start-click timestamp precedes READY, so click+30seconds is a
conservative earlier deadline for the descriptor duration. A window is refused
unless its duration plus an8second UI close margin fits. The registry's process
ceiling can be earlier still: continuous current/running checks fail shortened
coverage; they do not establish an atomic server hold. Android main-thread calls,
normal report completion and the real server cleanup remain separate runtime
boundaries, not a guaranteed wall-clock lease from this arithmetic.

The normal Back/continue/leave sequence is bound to the original captured Attempt.
Failure cleanup may cancel only that still-current object under its UI lock;
retiring an old Attempt cannot cancel a later one. The driver does not force-stop
the App/helper on this mode's failure, and owns no legacy sampler/input markers.
A local ADB reap alone is not phone/server quiescence. Failed or unknown cleanup
must keep the future coordinator's reservation/owned scope unresolved.

After normal exit and retiring completion, the helper requires no later current
Attempt and the expected cancellation generation before it reads the completed
App report under that UI lock. It exports a digest of those exact bytes; the
driver requires its subsequent read to match. The driver's actual instrumentation
output must contain one complete numeric result, one successful finish code and
no abort/failed/security markers. Existing first-session video, route, exit,
audio-thread, startup/stage and Surface readbacks remain required. The numeric
native export must be available and pass the existing closed consumer. OFF,
missing, changed, rejected or over64KiB whole reports fail rather than become
zero events. The native256/Java8192 rings and64 remaining-prefix export remain
unchanged; this mode also selects the existing Java Inbox history. Costs and
ART/JNI report acceptance are unmeasured.
