# M5 正式硬件串流：60 / 120 FPS 验收与部署

测试跨越 2026-09-29 至 2026-09-30。目标为原有、有应用与 root 模块的 `phone17-root`，未用干净副本替代。上一轮 [540P 实验](display-540-hardware-encoding-20260929.md) 的 22–23 FPS 与软件后端记录属于历史状态。当前 M5 正式后端已切换为必需苹果硬件 H.264 的 `videotoolbox`。

## 实际结果和验收边界

| 测试 | 有效测量窗口 | 实际 FPS | 输出间隔 P95 | 超过 33.4 ms 的间隔 |
| --- | --- | --- | --- | --- |
| 正式 TLS 服务，60 FPS，自适应 VBR 2.5→4 Mbps | 120.463 秒 | 60.002 | 20.037 ms | 0 |
| 正式 TLS 服务，120 FPS，自适应 VBR 2.5→4 Mbps | 120.699 秒 | 119.819 | 11.038 ms | 0 |
| 正式 TLS 服务，120 FPS，VBR 8 Mbps | 12.037 秒 | 119.965 | 10.415 ms | 0 |
| 正式 TLS 服务，120 FPS，CBR 8 Mbps | 12.040 秒 | 120.012 | 10.362 ms | 0 |
| 冷启动后正式 TLS，120 FPS，自适应 VBR 2.5→4 Mbps | 120.353 秒 | 119.973 | 10.352 ms | 0 |
| 冷启动后正式 TLS，V50 默认 30 FPS | 12.038 秒 | 29.987 | 35.182 ms | 173（正常 30 帧预算约 33.3 ms） |

原始结果见 [60 FPS 持续验证](evidence/display-540-20260929/gateway-60-sustained.json)、[120 FPS 持续验证](evidence/display-540-20260929/gateway-120-sustained.json) 及同目录的 8 Mbps 两组。接收平均值可能略超过目标，原因是窗口边界、到达抖动和计数误差，不代表显示器超过物理刷新率。120 Hz 对应理想 8.33 ms 间隔，实测 P95 大于这个值，不能说每一帧均无抖动。冷启动复测的最大间隔为 23.059 ms，超过两帧预算（16.67 ms）的间隔共 7 次；24 个完整 5 秒窗口中最低 119.8 FPS。30 FPS 复测没有超过两帧预算（66.67 ms）的间隔，不能把固定 33.4 ms 阈值用于判定其丢帧。详见 [120 冷启动复测](evidence/display-540-20260929/gateway-120-after-reboot.json)。

这些验证使用原账号 `huoguo`、M5 本机 TLS 和 App 的真实三个 CONNECT 通道，覆盖 H.264、AAC、安卓实际触摸和返回键、动态码率硬件确认、本机 H.264 解码。画面由合成 Activity 每帧更新；没有通过复制静态帧提高计数。账号口令仅在测试进程环境内，不写入报告或 Git。画面及压缩码流仅在内存内用于解码校验。

它们**没有经过 NPC / 腾讯 NPS 网络路径，也没有在一加或 V50 上实际播放**，因此不能当作手机公网 120 FPS 或端到端延时验收。音频为活跃的静音 AudioTrack→AAC 测试源；音频时间戳年龄是带时钟校准误差的估计，可能略为负数，不是声音播放延迟，也不能替代真机听感/音画同步测试。

## 为什么从 22 FPS 提高到 60 / 120 FPS

逐项比较的部分结果如下，完整报告保留于同目录。不同目标帧率的场景有不同负载，应在对应行内比较，不能把所有差异归给一个参数。

| 配置/变化 | 场景目标 | 实际采集及硬件输出 FPS |
| --- | --- | --- |
| 原配置：8 vCPU / 24 GB、pipe、默认刷新/后台调度 | 30 | 前轮 22.4 / 23.2 |
| 改为 4 vCPU / 24 GB，ASG | 30 | 29.1 / 28.8 / 28.0 |
| 4 vCPU / 8 GB、ASG、虚拟物理 120 Hz | 30 | 29.7 / 30.0 / 29.2 |
| 4 vCPU / 8 GB、ASG、min/peak 120、Vulkan HWUI | 60 | 53.867 / 54.067 / 54.533 |
| 同上，只改回 8 vCPU | 60 | 58.667 / 53.933 / 53.733 |
| 8 vCPU / 8 GB，同上并把 VM LaunchAgent 改为 Interactive | 60 | 60.067 / 60.133 / 60.067 |
| 当前配置，真正 120 FPS 绘制源 | 120 | 119.25 / 119.667 / 119.833 |

本轮对照表明：只增加 CPU 核数不足以解决，源端帧调度和图形传输同样影响供帧。Interactive 变化后的 Choreographer 回调接近实际 120 Hz，之前 60 目标在部分配置仍有明显少回调/漏绘。Vulkan 的合成测试 GPU 完成等待 P95 约 0.2–0.4 ms，硬编回调 P95 约 3 ms，说明此时硬件编码没有把该尺寸限制在 60 FPS。[120 目标源/采集分层报告](evidence/display-540-20260929/original-120-interactive-core8.json)

这些是该 M5、该 SDK、合成界面的实测；不能据此断言任意 App 使用 Vulkan 都更快、8 GB 一定比 24 GB 快、更多核心一定慢。源端 UI 线程、图形 API 翻译、时序、原始帧复制和网络队列都仍有 CPU 工作；“用硬件编码”不等于所有步骤没有开销。

## 最终配置及自动恢复

- ARM64 `arm64-v8a`、8 vCPU、8 GB 内存，苹果 Hypervisor.Framework，`-gpu host`。
- AVD 物理屏幕 `540×1200 / 210 dpi`，`hw.lcd.vsync=120`；`hw.gltransport=asg`。
- 安卓 `debug.hwui.renderer=skiavk`；`min_refresh_rate` 与 `peak_refresh_rate` 均为 `120.0`。
- VM 与网关 LaunchAgent 均为 `ProcessType=Interactive`，既有 RunAtLoad / KeepAlive 保留。
- 网关环境 `DIRECT_VIDEO_BACKEND=videotoolbox`、`DIRECT_REFRESH_RATE=120`、`DIRECT_HWUI_RENDERER=skiavk`。绘制配置按 boot_id 缓存，每次安卓启动后重新应用并读回校验。
- 退出串流后 300 秒息屏；重连唤醒，不关闭 VM。120 Hz 是亮屏策略，不会阻止息屏计时。

冷启动前后第三方应用均为 19 个，应用包名清单摘要相同，root UID 为 0；Vulkan 和 min/peak 120 自动恢复。NPC 连接仍显示物理网卡源地址 `192.168.9.126` 连接腾讯 `146.56.249.175:8024`。发布时进一步读回确认当前地址属于 Wi-Fi `en0`，有线优先接口 `en11` 此时不存在；现有 `en11,en0` 顺序回退到物理 Wi-Fi，不应把它记录为有线连接。本轮没有修改 NPC 或 Clash 网络配置。[重启读回](evidence/display-540-20260929/hardware-reboot-check.json) 未擦除用户数据或修改 root 模块。Mac 自身重启后，LaunchAgent 仍需用户会话已登录才启动；本轮验证的是现有用户会话中的 VM 冷启动。

`120 Hz` 是虚拟显示模式和刷新策略，`120 FPS` 是串流上限；30/60 帧的视频、静止页面或自行锁帧的应用不会产生 120 张不同画面。App 选择帧率不会突破内容帧率、手机屏幕或解码器能力。Google 的 Frame Rate API 也明确说明刷新率请求不是系统一定执行的保证。[Google 帧率说明](https://developer.android.com/media/optimize/performance/frame-rate)

## 正式硬件链路

```text
Android app / SurfaceFlinger
 → host GPU / gfxstream / Vulkan
 → authenticated loopback gRPC complete RGBA
 → bounded latest-frame slot
 → Accelerate vImage RGBA→BGRA / IOSurface pixel pool
 → required Apple VideoToolbox H.264 (no B frames)
 → original TLS stream protocol / Mac NPC / NPS
 → phone MediaCodec hardware decode / timed Surface presentation
```

宿主 GPU 绘制与 VideoToolbox 视频编码是独立环节。Google 官方推荐 ARM64 匹配宿主架构，并说明 `-gpu host` 可在 macOS 启用 MoltenVK；Mac VM 加速使用 Hypervisor.Framework。[Google 模拟器加速](https://developer.android.com/studio/run/emulator-acceleration)

540×1200 RGBA 每帧 2,592,000 字节，120 FPS 约 311 MB/s，只在本机原始帧链路传递。公网仍传目标 4/8 Mbps 的 H.264。使用完整帧，不为减少复制开启会有撕裂风险的共享内存读取。上游只有一个待处理完整帧，原始帧过时可替换；不能随意丢弃已编码 H.264 预测帧。

Swift 编码器强制并读回 `using_hardware=true`，实际 `com.apple.videotoolbox.videoencoder.ave.avc`；VBR / 自适应使用 AverageBitRate，CBR 使用实际受支持的 ConstantBitRate。CBR 是编码器目标，不做网络填充或保证每毫秒流量相同。专有 `MaxFrameDelayCount` 设置仍不受支持，没有把错误读回当作成功。

音频和输入保留官方 scrcpy 4.1 服务，视频关闭。音频用 8 次宿主/客体单调时钟往返校准选择最低 RTT 样本，映射到宿主视频时钟，避免客体墙钟偏差导致数百毫秒不同步。控制码率请求只在编码器就绪后提交，成功才确认。退出只清理本次 scid 的 guest 服务，支持立即再次连接。

## 代码与部署材料

核心为 [`hardware_stream.py`](../hardware_stream.py)、[`performance_profile.py`](../performance_profile.py) 与 [`gateway.py`](../gateway.py)。网关本身只引入标准库；gRPC 在单独进程和虚拟环境中，三个媒体通道用私有 Unix socketpair，不增加网络监听。

M5 的既有 `direct/hardware` 私有目录包含：

- `venv/bin/python`：与宿主 Python 3.14 匹配的 grpcio 1.84.0、protobuf 7.36.2 环境。
- `proto/emulator_controller_pb2*.py`：根据已安装 SDK 的 `emulator_controller.proto` 生成。
- `macos-h264`：`scripts/probes/emulator_hardware_encoder.swift` 通过 `xcrun swiftc -O` 编译。
- `scrcpy-audio-control`：本仓库 `stream-server:assembleRelease` APK，包含 `StreamClock` 辅助类；保留原服务协议。

编译说明在 [探针说明](../scripts/probes/README.md)。选择硬件后端前须部署上述材料；缺失/失败明确返回 503，不静默切回 guest 软件编码。其他机器默认仍为 `guest`，120 FPS 只接受于硬件后端，防止错误参数中断已有连接。

## 手机升级与建议

v1.17 增加 120 FPS 可选档和相应手机刷新率请求，保留已有 30/60 档与保存参数；恢复优化前设置也能恢复 120 选择。V50 首次默认/一键预设仍为 540P、自适应 VBR、4 Mbps、30 FPS、100 ms，用户手动选择不会被 v1.17 覆盖。正常自动检测仍用固定 30 FPS 场景，不能把它的报告用于宣称 120 已验收。

一加测试可以先选 540P / 120 FPS / VBR 或自适应 4 Mbps，若内容或网络条件需要，再尝试 8 Mbps。120 FPS 不自动需要 8 Mbps，也不自动提高视频本身质量；相同码率下每帧预算会减少。V50 先看 30/60 的真实显示 FPS、温度、掉帧和移动 Wi-Fi 线路，再决定是否尝试 120。

## Google 原版和 MuMu Mac 的比较

没有可靠依据证明“Google 原版必然比 MuMu 更快、更稳”。开源可调和平台来源不能代替同机同负载比较。网易 Mac 官方的《火影忍者》120 帧步骤包含设备型号/高配 GPU 标识、特定分辨率、6 核与 6 GB、提高帧率上限和游戏内开启；并提醒实际显示受 Mac 屏幕限制。它证明特定游戏可设高帧率，不证明短视频、root 模块或远程公网同样达到 120。[MuMu Mac 120 帧教程](https://mumu.163.com/mac/faq/how-to-set-120-frames-per-second-in-naruto.html)

MuMu Mac 还有特定游戏高画质适配，官方说明会增加占用，游戏更新可能导致适配失效。[官方图形适配说明](https://mumu.163.com/mac/tutorials/graphics-enhancement.html) Google 的 gfxstream 也有客体→宿主图形 API 转发层，不是 Android 直接无开销运行苹果 GPU。[gfxstream 开源实现](https://github.com/google/gfxstream)

本轮没有安装 MuMu、购买服务或做 MuMu A/B，所以没有给出两者的性能排名。当前 Google 实例已验证接近 120 的服务端视频链路，并保留所需 root、模块、应用和自动化接口；据此先用已实测的方案继续手机公网验收。
