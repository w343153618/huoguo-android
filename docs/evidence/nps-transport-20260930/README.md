# NPS TCP / QUIC / KCP 隔离实测（2026-09-30）

测试对象是 djylb/nps 0.34.7 的独立实例。腾讯云测试实例临时开放 TCP 18024（bridge）、UDP 8024（KCP）、UDP 8025（QUIC）和 TCP 15557（指向 M1 测试网关）；正式 NPS 的公网 15556 与原 TCP NPC 没有改。M1 的 NPC 通过仅监听回环地址的 relay 连接测试 bridge；relay 用 macOS `IP_BOUND_IF` 绑定有线 `en9`，服务端看到的是南京家庭国内公网来源。前一阶段采样结束后停止了独立实例；下午为真机对照重新启动。各阶段退出状态见下面“真机补测”记录，正式 NPS 始终保留。

`benchmark_nps_transport.py` 通过公网 15557 测 TLS `/ping`；同机同脚本、每种传输两轮各 60 次。成功请求的耗时如下：

| 路线 | 成功/尝试 | 往返中位数 | p95 | 最慢 |
| --- | ---: | ---: | ---: | ---: |
| TCP 第一轮 | 60/60 | 124.29 ms | 143.94 ms | 152.68 ms |
| QUIC 第一轮 | 58/60 | 115.40 ms | 825.40 ms | 4803.92 ms |
| TCP 第二轮 | 60/60 | 119.97 ms | 138.23 ms | 144.45 ms |
| QUIC 第二轮 | 60/60 | 119.94 ms | 138.00 ms | 164.67 ms |

真实视频探针用 M1 Android 虚拟机中的 YouTube App 播放同一视频 URL，网关请求 60 FPS、4 Mbps、自适应 VBR、VideoToolbox H.264；探针经腾讯云 TCP 15557 接收 H.264 与 AAC，不运行手机解码/显示。每次 35 秒，排除启动前 3 秒后的结果：

| 路线 | 接收均值 | 每秒收帧 p10 / 最低 | 帧到达间隔 p95 / p99 / 最长 | 视频 PTS 间隔 p95 | 视频到达年龄中位数 | 音频到达年龄中位数 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| QUIC（带音画年龄采样） | 25.22 FPS | 23.1 / 21 | 85.68 / 123.54 / 218.56 ms | 65.80 ms | 49.07 ms | -73.00 ms |
| TCP（带音画年龄采样） | 33.28 FPS | 30.1 / 29 | 58.46 / 71.38 / 88.59 ms | 48.85 ms | 30.89 ms | -11.52 ms |

另一次 45 秒 QUIC 视频样本曾有 1087.98 ms 接收间隔；35 秒 QUIC 复测最长 174.55 ms。不同轮次的源端 PTS 节奏和实际码率也不同，不能把 25.22 与 33.28 FPS 的全部差异归因于 QUIC。这里的“年龄”是接收时本机时钟减源时间戳，音频出现负值与源端 AAC 时间戳语义及时钟映射有关；两种媒体年龄的差值**不是手机扬声器和屏幕的实测音画偏差**。它提示音视频经独立通道到达的时间可能不同，仍须在手机上测实际显示/播放时刻。

KCP 客户端发出的 UDP 报文和服务端响应都能观察到，但 NPC 0.34.7 未完成测试 bridge 登录，`/ping` 60 次均失败。将 NPC 放在云服务器本机连接 `127.0.0.1:8024` 也未登录成功，因此这一阶段不能将故障归给南京到腾讯云的网络。下午已定位并修复隔离实例的配置握手权限，KCP 真机补测成功，见下文。

当前证据没有显示 QUIC 稳定优于 TCP。手机→NPS→网关中，手机到 NPS 这一段仍是 TLS/TCP；本测试只替换 NPC 到 NPS 的 bridge 协议。M5 当天离线，因此未迁移正式 M5 NPC，亦未完成一加 15 移动流量或东北 V50 的同条件播放对照。原始 JSON 和探针源码保存在本目录及 `scripts/probes/`。实验用固定 TCP relay 源码在 `experiments/nps-transport/`；不含运行凭据。


## 真机补测：家庭 CGNAT，经腾讯云中转

2026-09-30 下午，一加 15 的原 v1.21 客户端通过独立 Instrumentation 自动采样，不替换正式 App，不用截图计数。手机在家庭 Wi-Fi，M1 540×1200 Android 17、6 核/8 GiB；真实 YouTube App 播放 `dQw4w9WgXcQ`。每轮重新启动播放器，请求 60 FPS 上限、4 Mbps 自适应 VBR、80 ms 缓冲，手机实际使用 `c2.qti.avc.decoder.low_latency` 硬解。每轮约 45 秒，均值排除前 3 秒；显示间隔来自 MediaCodec 的实际呈现时间戳，间隔统计包含启动阶段。

家庭爱快 WAN 为运营商内网地址，观察到 `100.87.188.117`；电信做 NAT 后的国内出口是 `180.111.118.161`。这不等于家庭获得可入站公网地址。NPS 路线全部为手机 → 腾讯公网 15557 → M1 主动建立的 NPC → 本地网关，不依赖家庭入站端口。NPC 经固定 relay 绑定 M1 Wi-Fi `en0` / `192.168.9.125`，云端读回相同国内 NAT 出口。

Tailscale 使用另一个临时、同用户的 userspace 测试节点 `100.65.0.3`，`TS_DEBUG_ALWAYS_USE_DERP=1` 禁止 UDP 直连；日志和活动状态确认 `DERP(headscale)`，不是同 Wi-Fi 的局域网直连。外层中继在同一腾讯服务器的 HTTPS 443。M1 当时另有有线 `en7` / `192.168.9.128`，系统国内路由经该接口；它与绑定 en0 的 NPS 并非严格相同网卡条件。该临时节点不是给手机新增登录账号；所有视频连接使用既有 huoguo 账号。

| 路线 | M1 原始抓帧均值 | 提交编码均值 | 手机接收均值 | 手机显示均值 | 显示间隔 p99 / 最长 | >100 ms 显示间隔数 | 内部解码补偿均值 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| NPS TCP | 36.03 | 35.75 | 35.68 | 35.13 | 69.09 / 127.52 ms | 5 | 183.89 ms |
| NPS QUIC，播放器重启后的第二轮 | 33.11 | 31.87 | 31.92 | 31.61 | 77.29 / 278.48 ms | 10 | 200 ms |
| NPS KCP，修正配置后 | 25.62 | 25.56 | 25.63 | 23.78 | 164.05 / 336.92 ms | 38 | 200 ms |
| Tailscale，强制腾讯国内 DERP | 25.63 | 25.60 | 25.63 | 24.16 | 126.73 / 248.13 ms | 22 | 200 ms |

原始抓帧和提交编码是网关原有每 5 秒自动采样；根据真机报告完成时刻减采样时长近似对齐，取完整窗口并排除启动期，每行 7 个窗口。原始事件单独存为 `phone-*-pipeline.json`，仅保留性能事件，不复制运行日志里的会话信息。第一轮 QUIC 视频已播放一段时间后才开始测，码率明显偏低，不纳入上述重启片源比较，其 JSON 保留供审计。

**判断边界：**这些是经过腾讯中转的真实手机视频结果，但仅家庭 Wi-Fi、单段片源、短时样本。TCP 此轮显示间隔较稳定，不能由此认定协议永久优于其他路线，因为源端原始出帧已在 25–36 FPS 之间变化。KCP/DERP 两轮源端只有约 25.6 FPS，手机接收几乎相同，说明帧率上不去首先发生在抓取/源画面这一侧；手机呈现又有额外逾期丢帧。60 是串流上限，不代表视频内容原生 60 FPS，本测试没有验证片源的原生帧率。没有证明 60/120 FPS 已达成，也没有完成移动流量、异地 Wi-Fi 或东北 V50 验收。

四条路线均出现约 170–200 ms 的 `decoderHoldNs`，80 ms UI 缓冲不是总播放延时上限；AudioTrack 软件队列约 130–136 ms。后续应修正播放队列/时钟补偿并同时测源节奏，不能仅换传输协议或进一步增大缓冲。采集了 AudioTrack 播放位置，但没有 PCM 源 PTS 到播放帧的映射，因此这里仍未测出真正的扬声器/屏幕音画偏差。网络 RTT 只是控制小包往返，不是触控到显示延时。

### 本次修复与网络状态

- M1 重启后旧 `local.remoteandroid.direct` 服务抢占 15556，返回不支持 `/ping` 的旧网关。已备份旧 plist，禁用该旧任务，恢复 `local.remoteandroid.m1compare.gateway`；旧运行目录和 AVD 均保留。
- KCP 本机复测堆栈卡在 `client.StartFromFile` 读取 WORK_CONFIG 回复。隔离客户端 `ConfigConnAllow=false`，服务端源码在此直接关闭连接；KCP 没有像 TCP/QUIC 那样及时结束这次读取。仅将实验实例的这个配置改为 true 并重启实验服务，随后 KCP 登录成功且真实手机视频完成。正式 NPS 配置没有改。源码依据为 [djylb/nps v0.34.7 handshake.go](https://github.com/djylb/nps/blob/v0.34.7/bridge/handshake.go) 与 [control.go](https://github.com/djylb/nps/blob/v0.34.7/client/control.go)。
- Headscale 0.29.4 已启用腾讯国内 embedded DERP：region 999、HTTPS 443、UDP/STUN 3478、客户端验证开启。备份在云端 `/opt/headscale/backup-derp-20260930-155517/`。先通过 `tailscale debug derp headscale` 验证 IPv4 DERP 和 STUN，再去掉默认境外 DERP map；现有地图仅 region 999。无 IPv6 DERP，单一中继是可用性单点，国内中继失效时不自动改走境外。
- M1 Clash TUN 保持开启；修正并应用腾讯 /32 与 tailnet /16 的路由排除、Headscale 真 IP 和 fake-IP 例外。既有 Script.js 规则扩展后保留，运行配置通过 Unix socket API 重载并验证，腾讯实际国内 route 经 en7；NPS relay 仍独立强制 en0。备份在用户受限配置目录，代理订阅/密钥不入仓库。上述仅验证 M1 当前出口，不代表 M5 后续已验证。
- 探针使用一次性受限文件传递既有账号凭据，App 消费后删除；不硬编码或记录密码。已读回确认手机保存的 120 FPS 用户选项保持不变，修复探针退出时恢复原参数的逻辑；正式 App 版本不变。

参考：[Headscale DERP 配置](https://headscale.net/stable/ref/derp/)。DERP 用于直连失败后的连通性保障，官方没有承诺更高吞吐或更低延时。
