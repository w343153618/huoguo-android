# M5 公网会话启动 503 修复

2026-10-03，用户在一加15使用正式 App，M1 公网可连接，M5 公网备选报告“服务启动失败503”。本轮优先修复 M5 日常线路；M1 继续作为机主实验环境，不将实验 worker 整体部署到 M5。

## 两个连续的失败阶段

M5 gateway 的参数验证已经接受 `768/960/1200/1280/1600/1920/2400`，部署的硬件 worker CLI 却仍只接受 `960/1200/1600/2400`。`hardware/worker.log` 最后连续四次显示 `1920` 被 argparse 拒绝，worker 在初始化之前退出，gateway 返回503。标准720P的1280与较低档768有同样的兼容问题。

第一处修复只对齐 M5 旧 worker 的 CLI 白名单，不替换其原生编码器、Python环境或完整实验源码。修复后用户再次连接，日志进入新的 `RuntimeError`，音频初始化尚未发生。只读检查确认 M5 同时运行一个本地 `scrcpy -s emulator-5554`，guest 对应 scrcpy3.3.4/scid22706422；它触发现有 `existing guest stream` 启动保护。gRPC发现文件、token存在性、运行时及ADB启动状态均正常。

确认没有正式在线会话后，仅向经过命令读回确认的本地镜像进程PID31850发送TERM，guest镜像进程自然消失。虚拟安卓、gateway、NPC及NPS均没有重启；应用数据、账号和保存密码没有修改。保留独占保护，没有用删除启动检查的方式绕过冲突。M5日常使用时不再同时开启这个本地scrcpy镜像；若今后需要本地预览，应另行实现不会占用正式输入/音频通道的预览模式。

- M5公网 `146.56.249.175:15558` 与局域网 `192.168.9.99:15556` 使用App内受信M5证书验证，ping正常；公网更新manifest仍是正式v1.30/code31。

- M5腾讯目标路由仍是192.168.9.1/en11；没有改Clash、NPS主程序、NPC身份或国内来源过滤。这是路由读回，不是逐包外层出口抓包。
